# Slate v0.2 build plan

Source: 27 improvements reported from a real project (Gurukul: ~58 tickets, stacked PRs,
parallel agents, git worktrees). Numbers below (#1–#27) match that list. Version **0.2.0**,
board schema **2**. Backwards compatible: v1 boards load, `migrate` upgrades them additively.

Existing contracts in `2026-09-26-v0.1-build-plan.md` still hold unless changed here. Every new
error/refusal keeps the `error: <ID> <field>: …` + `fix: <command>` / `ask the user: …` shape.
Every write still validates the whole board and writes atomically.

## Schema 2 (all new fields optional; v1 boards stay valid)

- `meta.statuses` default: `draft backlog ready in_progress review user_testing merge_ready done`.
  `migrate` 1→2 inserts `merge_ready` right before `done` if missing; sets `schema_version: 2`.
- `meta.check_quiet_optional` (bool, default false) — same effect as `check --quiet-optional`.
- `phases[].unscheduled` (bool). Phase ids are any `^[A-Za-z][A-Za-z0-9_-]{0,19}$`, e.g. `BACKLOG`.
- `phases` array order = display order.
- `tickets[].item_checks`: `{ "acceptance:0": {"date": "YYYY-MM-DD", "evidence": "…"}, "test:2": {...} }`.
- `meta.unlock_log`: `[{ "date": "YYYY-MM-DD HH:MM", "reason": "…", "minutes": 5, "until": "ISO" }]`.
- Unlock record file (not board data): `kanban/.slate-unlock.json` `{ "until": "<ISO UTC>", "reason": "…" }`.

## A — board.py core

1. `edit-phase ID [name=…] [goal=…] [demo=…] [unscheduled:=true|false]`.
2. `rename-phase OLD NEW` — re-points every ticket's `phase`, atomic.
3. `remove-phase ID [--move-to OTHER]` — refuses while tickets use it unless `--move-to`.
4. `reorder-phases ID ID …` — must list every phase exactly once.
5. Unscheduled phases: `add-phase … --unscheduled`; `next`/`list` never offer their tickets;
   `status` and `show` list them last; `set ID in_progress|review|user_testing|merge_ready|done`
   on a ticket in an unscheduled phase refuses with `fix: … edit ID phase=<scheduled phase>`;
   `promote` from an unscheduled phase succeeds but prints a hint to move it.
6. Repeated list flags accumulate (argparse `append`) for `--labels --areas --depends
   --acceptance --test --user-test-json`. Comma lists additionally split for `--labels --areas
   --depends` only (acceptance/test sentences contain commas).
7. `edit ID field+="text"` appends (blank line between) for `description technical story summary visual`.
8. `new --bug --fixes ID,ID …`: adds labels `bug` + `fixes-<ID>`; each fixed ticket gets the new
   ticket in `depends_on`; new ticket is ranked right before the earliest fixed ticket. If a fixed
   ticket is `done` (or `merge_ready`), refuse with `ask the user:` to reopen, and offer
   `--reopen` which moves those tickets to `in_progress` with a handoff note.
9. `edit ID depends_on:=[…] --rerank` (and `edit … --rerank` generally): move the ticket right
   after its latest dependency if needed. The existing rank error must print the `--rerank` fix.
10. `set ID STATUS --ignore-deps "reason"` allowed for `in_progress review user_testing` only;
    appends `(deps open: <IDs> — <reason>)` to the handoff note. `merge_ready`/`done` stay strict.
11. Bulk: `set ID1,ID2 STATUS --handoff …` and `link ID1,ID2 --pr URL` (also `--pr-state`).
    All-or-nothing: validate every ticket first; on any refusal nothing is written.
12. `export --json [--phase P] [--status S] [--label L] [--area A] [--drafts]` → full tickets.
    (`show --json` already exists.)
13. Same filters on `list` and `status`.
14. `check --quiet-optional` hides optional-field warnings (missing visual/technical); honours
    `meta.check_quiet_optional`; prints "N optional warnings hidden".
26. `check-item ID acceptance|test INDEX [--evidence "…"]` / `uncheck-item ID acceptance|test INDEX`.
    `show` renders `[x]` per checked item with evidence; done tickets still show all `[x]`.
27. `merge_ready`: `set ID merge_ready` requires every required user test passed, ≥1 commit
    linked (in a git repo), and a PR linked when the repo has a remote (or `--no-pr "why"`).
    `done`: if a PR is linked and its state isn't `merged`, refuse with fixes
    `link ID --pr-state merged` / `--no-pr "why"` (ask the user). Otherwise existing done rules.
    `next` lists `merge_ready` tickets under "Waiting for merge" (not resumable work).
- `migrate`/`upgrade`: 1→2 as above; bump `SLATE_VERSION = "0.2.0"`, `SCHEMA_VERSION = 2`.

## B — branches, worktrees, merges (after A)

15. `diff OTHER [--json] [--include-rank]` — OTHER = path to a tickets.json, a directory
    containing `kanban/tickets.json` or `tickets.json`, or a git ref (`git show REF:<repo-relative
    path>`). Per ticket: added / removed / changed fields. Ignores rank-only changes (unless
    `--include-rank`) and compares `handoff` by (status, note) ignoring dates.
16. `sync --from OTHER [--dry-run] [--only ID,…] [--prefer ours|theirs]` — applies OTHER's
    differences: new tickets and phases added (id clash with different content → error for that
    ticket), record lists unioned (`handoff`, `commits`, `user_checks`, `item_checks`), `status`
    takes the further-along one in `meta.statuses` order, other changed fields take theirs
    (default) or ours. Whole result validated; `--dry-run` prints the plan.
17. `merge-driver BASE OURS THEIRS` (git passes `%O %A %B`): three-way, per ticket and field:
    changed on one side → take it; same change → take it; both changed → record lists union,
    `status` further-along, `rank` recomputed, anything else = conflict (keep ours, report on
    stderr). Writes the merged board to OURS; exit 0 if no conflicts, 1 otherwise. Ranks are made
    unique and deps-first after merging. `install-merge-driver` writes `.gitattributes`
    (`kanban/tickets.json merge=slate`) and `git config merge.slate.driver "python3
    kanban/board.py merge-driver %O %A %B"` + `merge.slate.name "Slate board merge"`.
18. Board of record: on every write, warn (stderr, not fatal) when the git dir differs from the
    common dir (secondary worktree), naming the main worktree's board; when
    `SLATE_BOARD_OF_RECORD` is set and resolves to a different tickets.json; and when the default
    branch's board (`origin/HEAD`, else `main`/`master`, no fetch) has tickets or handoff entries
    this board lacks — with `fix: … diff <ref>` / `sync --from <ref>`.
19. `copy-to PATH [--force]` (alias `export-file`) — writes a validated copy to PATH (file, or
    `PATH/kanban/tickets.json` for a directory). Refuses when the target has changes this board
    lacks (per `diff`) unless `--force`.
21. **Unlock (final design: works in every setup, including SSH; no desktop pop-up).**
    **Human in the loop = the agent tool's own permission card.** Slate does not build any
    approval UI. The guard's PreToolUse hook answers `permissionDecision: "ask"` for every
    `board.py unlock` command, which makes Claude Code (or Copilot CLI, whose hooks support the
    same "ask") show its built-in approval card — the same card as accepting an edit — in
    whatever terminal the user is in, including over SSH. Clicking **Yes** is the approval; no
    code is typed on the card. Agent tools without hooks get no card, so there the only way to
    unlock is the typed-code terminal path below (safe by default, zero per-tool work).
    `unlock --reason "…" [--minutes 5]` (max 30; reason required). One unlock = **one** direct
    edit (the guard consumes it), expiring after `--minutes` if unused.
    - **Interactive terminal** (`sys.stdin.isatty()` and `sys.stdout.isatty()`): the person runs
      it themselves; it shows a random 4-letter code and asks them to type it; match (case-
      insensitive) → writes the active unlock `kanban/.slate-unlock.json`
      `{until, reason, created, approved: "terminal code"}`. Works over SSH and in any agent tool.
    - **Non-interactive** (run by an agent): writes only a **request**
      `kanban/.slate-unlock-request.json` `{id, reason, minutes, created}` and prints
      "Unlock requested. Approve it in the permission prompt (Claude Code / Copilot), or run
      `python3 kanban/board.py unlock --reason \"…\"` in your own terminal and type the code."
      It never activates an unlock itself.
    - **Activation after approval** is done by the guard in PostToolUse mode (see C-21b): only
      after the permission prompt was approved and the `board.py unlock` command ran.
    - `lock` removes any active unlock and pending request; logs it. `check`/`status` warn while
      an unlock or request is active. Every request, activation, use (folded in from
      `.slate-unlock.used.json`), refusal and lock is appended to `meta.unlock_log`.
    - Tests simulate the terminal with an injectable input function; never real prompts.

C-21a — SUPERSEDED 2026-09-26 by user decision: no ask-rule injection; bypass mode skipping the
card is accepted; Claude Code only, Copilot CLI support later. Original note kept for reference:
(permission modes, verified against code.claude.com docs 2026-09-26): hook "ask" is shown
in Manual, acceptEdits and **auto mode** ("auto mode still shows you those prompts"), but
**bypassPermissions skips hook prompts** — only explicit **ask rules** (and a few built-ins) still
prompt there. dontAsk and `-p` turn "ask" into a denial. Therefore:
- `/slate:init` and `/slate:upgrade` merge into the project's `.claude/settings.json`
  `permissions.ask`: `"Bash(python3 kanban/board.py unlock *)"`, `"Bash(python kanban/board.py
  unlock *)"`, `"Bash(py -3 kanban/board.py unlock *)"` (and the detected interpreter's form).
  The hook "ask" stays as a second layer.
- Activation (C-21b) only accepts a command that **starts with** one of those exact forms
  (after trimming), with no `&&`, `;`, `|`, backticks or `$(` — wrapped/disguised unlocks never
  activate, so the ask rule can't be dodged.
- Copilot CLI: its docs don't define "ask" under `--allow-all-tools`/`--yolo`/autopilot (cloud
  agent treats it as deny). Until verified, Copilot gets **no activation hook**: unlock there is
  the typed-code terminal path only.

C-21b (guard, done after B): `hooks.json` adds a `PostToolUse` entry (matcher `Bash`) running
`guard_tickets.py --post`. In post mode, if the command matched the same `board.py unlock`
pattern that triggers the PreToolUse "ask", and a fresh request file (created < 2 min ago) exists
next to the tickets.json, atomically convert it into the active unlock
(`approved: "permission prompt"`) and delete the request. The guard blocks direct writes to all
`.slate-unlock*.json` files. Copilot: same script via its `postToolUse` hook when Copilot
support lands. Drop every mention of a GUI dialog / tkinter / osascript / zenity.

C-21c — final gating (user decision, supersedes "bypass goes through" above): the guard reads the
hook input's `permission_mode`. PreToolUse on a `board.py unlock` command: `default`, `acceptEdits`,
`auto` (or the field missing, i.e. an older Claude Code) → "ask" card; `plan` → deny ("leave plan
mode first"); `bypassPermissions`, `dontAsk` or anything else → deny ("nobody is here to approve;
the user runs unlock in their own terminal and types the code"). PostToolUse activates only in
those same ask modes (or missing), only for the exact command forms, and records
`permission_mode` in the active unlock and so in `meta.unlock_log`. No Copilot-specific code;
docs say "Copilot CLI support: planned".

## P — portability pass (Windows, macOS, Linux), after B

- `board.py`: UTF-8 + `\n` for every read/write, UTF-8-safe stdout/stderr (done in A), pathlib only.
- Python command: hooks run through `hooks/run.sh <script>` which tries `python3`, `python`,
  `py -3` (first that runs Python 3.9+). `/slate:init` detects the same and records it in
  `SLATE.md` ("Python: `<cmd>`"); skills use that command; `install-merge-driver` writes it into
  the git config driver line; fix: lines print `<cmd> kanban/board.py …` using the interpreter
  that ran board.py when it is not `python3` (`sys.executable` basename heuristics).
- Guard: Windows paths (`C:\…\kanban\tickets.json`, backslashes, drive letters) and
  case-insensitive matching.
- CI: `.github/workflows/test.yml` — matrix `ubuntu-latest, macos-latest, windows-latest` ×
  Python `3.9, 3.13`; runs `pytest -q`; tests must not assume `/` paths, `python3` on PATH, or a
  POSIX shell except where skipped explicitly.

## D — parallel work and self-healing (added 2026-09-26, user-approved)

1. **Write lock.** Every command that changes tickets.json (read-modify-write) holds
   `kanban/.slate-write.lock`, created with `os.open(O_CREAT|O_EXCL)` and holding pid, host,
   time and command; it waits up to ~10 s (short randomised sleeps), then refuses with
   `fix: … unlock-write   (remove stale lock …)`. The board is read after the lock is held and the
   lock is always released (only our own). `unlock-write` removes a lock older than 60 s or whose
   pid is gone on this host (Windows: kernel query, never a signal), and refuses otherwise.
   `.gitignore` gets `kanban/.slate-write.lock`; the guard blocks direct writes to it.
2. **Claims.** Optional `tickets[].claimed_by: {"by", "since": "YYYY-MM-DD HH:MM"}` (schema stays 2).
   `set ID in_progress` claims for the current git branch (fallback `host-user`, override `--as`);
   `review`/`user_testing`/`merge_ready` keep it; every other status clears it. `next`/`list` skip
   tickets claimed by someone else and show `on: <name>`; `set` on such a ticket refuses with
   `ask the user:` + `--take-over "reason"` (recorded in the handoff note), except `done` (gated by
   the merged PR). `claim ID` / `release ID` (`--as`, `--take-over`). `status` lists claims.
   `edit` and batch files can't set `claimed_by`. The merge driver takes the later claim when both
   sides changed it.
3. **`doctor [--json] [--brief] [--against ROOT]`.** Local health checks, each with a `code`, a
   `kind` (`tickets`: `board-behind`, `board-errors`, `board-unreadable`; `setup`: everything else)
   and `fix` lines: `schema-outdated`, `board-files-outdated`, `plugin-outdated`,
   `python-cmd-missing`, `slate-md-missing`, `slate-md-sections`, `merge-driver-missing`,
   `gitignore-missing`, `repo-url-missing`, `write-lock-stale`, `unlock-active`, `board-behind`
   (fixes `diff <ref>` and `sync --from <ref> --dry-run`). Exit 0 healthy, 1 problems. `--brief`:
   one line (`Slate: 2 setup issues — run /slate:upgrade · board behind main — run /slate:sync`).
   The SessionStart `next --brief --against ROOT` appends it when there are issues.
4. **Repair writes.** A board that already has errors can be written when the change adds no new
   error and leaves strictly fewer (compared by ticket, field and message); board.py prints
   `repair: N errors left`. `sync` and unlock-log writes need only "no new errors"; `diff`,
   `merge-driver`, `unlock`, `lock` and `migrate` work on invalid boards; `copy-to` still copies
   only a valid board.

   `add-status NAME --after S|--first --like ROLE_OR_STATUS [--label]`, `rename-status`,

   Invariants refused by the commands (warned by `check`): a done-role status and a
   backlog/ready-role status must remain; no draft-role status → `new --draft` refuses with a fix.
   Labels shown by status/show/next/list; `export --json` adds `status_label`;
   `export --json --statuses` prints the setup.
7. **Path rules.** Optional `meta.status_from`; enforced by `set` (incl. bulk) for forward moves;
   backward moves need `--handoff` while rules exist; refusal names allowed previous statuses and
   the next allowed step. `set-meta workflow=strict|free`. promote, usertest fail, bug reopen,
   sync and the merge driver skip path checks (other checks still run). Deviation: the rules are
   printed by `export --json --statuses` (not inside `export --json`, whose output stays a list of
   tickets).

**Board server started automatically, never twice (user request):**
- `serve` writes `kanban/.slate-serve.json` {pid, host, port, url, started, board_path,
  slate_version} on start (foreground or background) and removes it on clean exit.
- `serve --ensure`: read the runtime file → verify pid alive AND `GET /api/info` answers with
  the same board_path → print the URL and exit 0. Otherwise clean up a stale file and start a
  detached background server (POSIX `start_new_session=True`; Windows
  `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP`), logging to `kanban/.slate-serve.log`, then print
  the URL. If the preferred port is taken by something else, try the next free port. If the port
  answers but is not a Slate server (e.g. `python3 -m http.server`), say "board open in view-only
  mode there; live mode at <url>".
- `serve --status` (read-only report), `serve --stop` (terminate the recorded pid, remove file),
  `--idle-exit HOURS` (default 8) to stop by itself when no request arrived for that long.
- Skills `plan`, `work`, `status`, `sync` run `serve --ensure` in step 0 unless SLATE.md says
  `Board server: off`; show the link once. SSH hint: `ssh -L <port>:localhost:<port> host`.
- SLATE.md template: `Board server: auto|off` (default auto); init asks; upgrade adds `auto` and
  mentions it. SessionStart hint appends the URL when a server is running.
- `.gitignore` (init/upgrade/doctor): add `kanban/.slate-serve.json`, `kanban/.slate-serve.log`.
- Tests: ensure starts once (second call reuses), stale file cleanup, foreign server on port,
  next-free-port, stop, idle exit (short timeout), runtime file contents.
- Port: `--port N` on `serve` / `serve --ensure` (default 8088); per-project default from SLATE.md
  `Board port: N` (init asks, upgrade adds 8088), skills pass it; taken port → next free port
  unless `--strict-port` (then refuse naming the port); the runtime file records the port
  actually used and every message prints the real URL.
- **Every board-page action saves in live mode** (API → same code paths): drag / status dropdown
  → `set` (prompt for a handoff note when the target requires one or the move is backward);
  acceptance/test ticks → `check-item`/`uncheck-item`; user test Pass/Fail (+ optional note) →
  `usertest`; "Clear result" → `usertest … reset`; new drawer "Add note" box → `note`; new
  "Promote" button on drafts → `promote`; new "Take"/"Release" buttons → `claim --as <name from
  a one-time prompt, remembered in localStorage>` / `release`. Disallowed status targets greyed
  (from gates + transition rules via `GET /api/allowed?id=…`), refused drags show reason + fix.
  History entries carry `via: "board page"`. View-only mode keeps them local with the copy
  button. Editing ticket text, creating/removing tickets, phases and states stay CLI/agent-only.
