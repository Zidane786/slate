# Upgrade to 0.2.0

## What's new

- **Agents always explain their moves:** every status change an agent makes carries a short note in the ticket's history, even into states where a note is optional for people.

Slate 0.2 grew out of a real project with about 60 tickets, stacked pull requests, several
agents at once and git worktrees. In plain words, you can now:

- **Click on the board and it sticks.** `python3 kanban/board.py serve --ensure` runs the board
  page with a live connection: ticking an item, Pass/Fail on a user test, moving a card, adding a
  note, taking or releasing a ticket all save to the board through board.py (same checks as the
  commands). Slate commands start it for you, never twice. Opened any other way the board is
  view-only, and "Copy as board.py commands" turns your clicks into commands. Over SSH:
  `ssh -L 8088:localhost:8088 <host>`.
- **See "Waiting for merge".** A new column between User testing and Done: built, reviewed,
  tested, PR linked. A ticket becomes Done only after you say the PR is merged —
  `python3 kanban/board.py link ACME-014 --pr-state merged`.
- **Tick items with evidence.** `python3 kanban/board.py check-item ACME-014 test 0 --evidence "test_reset_link"`.
- **Log bugs as their own tickets.** `python3 kanban/board.py new --bug --fixes ACME-004 --title "…" …`
  — the broken ticket waits for the fix.
- **Park someday ideas** in an unscheduled phase nobody picks from:
  `python3 kanban/board.py add-phase --id BACKLOG --name "Someday" --goal "…" --demo "…" --unscheduled`.
- **Shape your columns.** Add, rename, relabel, reorder or remove states; each behaves like a
  built-in role: `python3 kanban/board.py add-status qa --after review --like review --label "QA"`.
- **Choose which moves need a note for the ticket's history.** By default moving into Review,
  User testing, Waiting for merge or Done needs a note; change any state with
  `python3 kanban/board.py edit-status review note=optional` (or `add-status … --note required`).
- **Set workflow rules** (optional): `python3 kanban/board.py set-meta workflow=strict` makes
  tickets go Backlog → In progress → Review → User testing → Waiting for merge → Done without
  skipping; `edit-status qa from=review` sets one rule; `workflow=free` removes them.
- **Remove and restore tickets** without losing them:
  `python3 kanban/board.py remove ACME-011 --reason "duplicate"`, then `restore ACME-011`.
- **Add notes** without changing the status: `python3 kanban/board.py note ACME-014 "waiting on legal"`.
- **Fix mistakes with commands:** `unlink ACME-014 --commit 3f9c2a7`, `usertest ACME-014 0 reset`,
  several tickets at once with `edit ACME-004,ACME-005 phase=P3` and `set ACME-004,ACME-005 …`.
- **Work in parallel safely.** `set ACME-014 in_progress` **claims** the ticket for your branch;
  others skip it (`claim` / `release`, `--take-over` only with your OK). Several board.py
  commands at once take turns through a **write lock** (`unlock-write` clears a stale one).
- **Keep boards in step across branches and worktrees.** `diff main`, `sync --from main`
  (`/slate:sync` walks you through it), `copy-to PATH`, and a **git merge driver**
  (`python3 kanban/board.py install-merge-driver`) that merges tickets.json ticket by ticket.
- **Check health in one go.** `python3 kanban/board.py doctor` — setup problems go to
  `/slate:upgrade`, board problems to `/slate:sync`.
- **Supervised unlock** for the rare hand edit: `python3 kanban/board.py unlock --reason "…"`.
  In Manual, Accept edits and Auto mode Claude Code shows its approval card; in Plan, Bypass and
  Don't-ask mode you type a code in your own terminal. One unlock = one edit.
- **Filters and JSON for agents:** `export --json --status review --label bug`, same filters on
  `list` and `status`.

## Steps

These run after `python3 kanban/board.py upgrade --from "<ROOT>/assets/board"` has replaced the
board files, for projects whose board was older than 0.2.0. Ask one question at a time; keep
every value the project already set. `doctor` codes are named where `board.py doctor` reports
them.

### 1. Board schema 2
**Check:** `python3 kanban/board.py version --json` shows `schema_version` below 2, or `doctor`
reports `schema-outdated`.
**Do:** `python3 kanban/board.py migrate` (inserts `merge_ready` right before `done`, sets
`schema_version: 2`, then runs `check`). Nothing is deleted or renamed. If `check` fails
afterwards, fix it with the `fix:` lines it prints (ask before any fix that changes meaning).

### 2. Python command
**Check:** `SLATE.md` has no line `Python: \`<cmd>\``, or `doctor` reports `python-cmd-missing`.
**Do:** find the first of `python3`, `python`, `py -3` that runs Python 3.9 or newer
(`<cmd> -c "import sys; print(sys.version_info >= (3, 9))"` prints `True`). Tell the user which
one you found and ask: "Slate will run the board with `<cmd>`. OK, or use another command?"
Write the answer into `SLATE.md` under the "Board:" line as `Python: \`<cmd>\``. If it is not
`python3`, use it for every later command in this upgrade.

### 3. Git merge driver
**Check:** only in a git repo. Needed when `doctor` reports `merge-driver-missing` (or
`git config --get merge.slate.driver` prints nothing or names another Python command than step
2's, or `.gitattributes` lacks `kanban/tickets.json merge=slate`).
**Do:** tell the user: "Slate can merge the board ticket by ticket when git merges branches,
instead of leaving conflict markers in tickets.json. It adds one line to `.gitattributes`
(committed) and sets the driver in this clone's git config (each teammate's clone gets it when
they run /slate:upgrade or /slate:init). Set it up?" On yes:
`python3 kanban/board.py install-merge-driver` (add `--python "<cmd>"` if step 2's command isn't
`python3`; safe to re-run).

### 4. `.gitignore` lines
**Check:** `.gitignore` lacks any of the lines below, or `doctor` reports `gitignore-missing`.
An older `kanban/.slate-unlock.json` / `kanban/.slate-unlock.used.json` line is covered by the
glob and may stay.
**Do:** ask, then append only the missing lines (create `.gitignore` if there is none):

```
# Slate: local files (never commit)
kanban/.slate-unlock*.json
kanban/.slate-write.lock
kanban/.slate-serve.json
kanban/.slate-serve.log
```

If `git ls-files kanban/` lists any of those files, tell the user they were committed by
mistake and suggest `git rm --cached <file>` (don't run it without a yes).

### 5. Board server
**Check:** `SLATE.md` has no `Board server:` or `Board port:` line.
**Do:** explain: "Slate can now keep the board page running for you, so clicks on it (ticks,
Pass/Fail, moving cards, notes) save to the board. Slate commands start it when needed, never
twice, and it stops by itself after 8 idle hours." Ask "(a) auto (recommended) (b) off — I'll
open it myself", then "Port: (a) 8088 (b) another". Write both lines under the `Python:` line:

```
Board server: auto
Board port: 8088
```

Change the "Board:" line's open command to `<python> kanban/board.py serve --ensure --port <port>`.
Over SSH the user forwards the port: `ssh -L <port>:localhost:<port> <host>`.

### 6. Setup questions new in 0.2 (asked by `/slate:init` since 0.2.0)
Ask each only when `SLATE.md` (or `doctor`) shows it isn't answered yet; write the answers into
`SLATE.md` under "Rules" or "Board of record" (never inside `## Workflow`, which is generated).

1. **Parallel work.** Check: `SLATE.md` says nothing about how the team works. Ask: "Do several
   people or agents work on this repo at the same time — in separate branches or git worktrees?
   (no / branches / worktrees)". If branches or worktrees, ask: "Which board is the board of
   record? (default: `kanban/tickets.json` on `<default branch>` in the main checkout / another
   path)". If they choose a path, tell them that setting `SLATE_BOARD_OF_RECORD=<absolute path
   to that tickets.json>` in each worktree's shell makes board.py warn when writing elsewhere
   (Slate doesn't set environment variables for them). Mention claims and the write lock in
   one line each.
2. **Repository address.** Check: `doctor` reports `repo-url-missing`. Do: its `fix:` line has
   the address from `git remote get-url origin` (an SSH form turned into `https://host/group/repo`).
   Ask: "Link commits on the board to `<url>`? (yes / another address / no)". Yes →
   `python3 kanban/board.py set-meta repo_url=<url>`.
3. **Someday ideas.** Check: `python3 kanban/board.py status` shows no unscheduled phase. Ask:
   "Add an unscheduled `BACKLOG` phase for someday ideas that aren't planned yet? `next` and
   `/slate:work` skip it. (yes / no)". Yes →
   `python3 kanban/board.py add-phase --id BACKLOG --name "Someday" --goal "Ideas worth keeping, not planned yet" --demo "Nothing to demo; move a ticket to a real phase to build it" --unscheduled`.
4. **Who merges pull requests.** Check: `SLATE.md` doesn't say who merges. Ask: "Who merges
   pull requests here? (you / a reviewer or maintainer / CI after approval)". Write one line
   under "Rules",
   e.g. "PRs are merged by <who>; Slate marks a ticket done only after they tell it the PR is
   merged." Slate never merges, whatever the answer.

### 7. Custom states and workflow rules (default: keep as is)
**Check:** `python3 kanban/board.py export --json --statuses` shows the default states and
workflow `free`, and `SLATE.md` doesn't record a decision about states or rules.
**Do:**
1. Run `python3 kanban/board.py flow` (the moves tickets really made, with counts). If `flow`
   isn't in `--help` (an older board), read the handoff history with `export --json` and count the status
   changes yourself, or just ask the questions in 3.
2. Turn it into a plain recommendation with a picture, e.g.:

   ```
   What your tickets did:  In progress → Review 41 · Review → User testing 31 ·
                           User testing → Waiting for merge 30 · In progress → Done 2
   Recommended (strict):   In progress ─▶ Review ─▶ User testing ─▶ Waiting for merge ─▶ Done
   ```

   "Your tickets nearly always go Review → User testing → Waiting for merge → Done. Lock that
   in? 2 tickets skipped Review — keep that possible?" If the history shows a step the board
   has no column for (notes like "QA passed"), offer a state for it:
   `python3 kanban/board.py add-status qa --after review --like review --label "QA"`.
3. Ask "(a) keep things as they are (default) (b) apply the recommendation (c) change
   something". Only on (b)/(c): `python3 kanban/board.py set-meta workflow=strict`, or per rule
   `python3 kanban/board.py edit-status <state> from=<a,b>`; `add-status` / `edit-status … label=…`
   for agreed states. For each new state ask whether moving into it needs a note for the
   ticket's history (`--note required|optional`, default as the state it is like). Show the
   final path as a picture.
4. Write one dated line under "Decisions" in `SLATE.md` either way ("kept free workflow" /
   "strict workflow, QA column"), so the check comes back "not needed".

### 8. New `SLATE.md` sections
**Check:** `doctor --against "<ROOT>"` reports `slate-md-sections` or `slate-md-workflow-stale`,
or any of these headings is missing: "Workflow", "Board of record (branches and worktrees)",
"Bugs", "Unscheduled phases", "Ticks, merges and unlocks", "Slate updates".
**Do:** add each missing section from `<ROOT>/templates/SLATE.md`, filling `{{PREFIX}}` and the
other placeholders from the project and the answers above:
- `## Workflow` → exactly the output of `python3 kanban/board.py workflow --markdown` (it includes
  the heading and describes states, rules, user tests, bugs, BACKLOG, board of record, merge
  driver, Python command and the unlock rule). Add nothing inside it: `doctor` compares it word
  for word. Run it last, after steps 1–7, so it reflects their answers.
- `## Slate updates` → the dated line `/slate:upgrade` writes (e.g.
  `2026-09-26 · Slate 0.1.0 → 0.2.0: live board, custom states, workflow rules, claims, remove/restore, notes, doctor, sync + merge driver, waiting for merge, bug tickets`).
Refresh the first line to `<!-- slate v0.2.0 · written by /slate:init, safe to edit values -->`.
Change no existing value.

### 8b. Agent note rule

- **Check:** `SLATE.md`'s `## Rules` section lacks the line about agents adding a note on every
  status move.
- **Do:** add this line under `## Rules` (no question needed; it only affects agents): "Agents add a
  short note for the ticket's history on every status move they make, even where the note is
  optional (what was done, or why it moves). People on the board page may skip optional notes."

### 9. Run `doctor` until healthy
**Check:** `python3 kanban/board.py doctor --against "<ROOT>"` reports any problem.
**Do:** for each `setup` problem, run its `fix:` line after telling the user what it does (ask
first when it touches files the project owns). Re-run until it reports no setup problems and
`python3 kanban/board.py check` passes. `ask the user:` lines are questions: ask them.

### 10. Ticket problems → suggest `/slate:sync`
**Check:** `doctor` reports problems of kind `tickets` (`board-behind`, `board-errors`,
`board-unreadable`), or board.py printed a board-of-record warning during this upgrade.
**Do:** don't sort them out inside the upgrade. List them and say: "The board here and the one on
`<ref>` differ. Run `/slate:sync` to see the differences and choose what to bring across."
